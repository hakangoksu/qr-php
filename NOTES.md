# NOTES

Design decisions, their reasons and their costs. The README explains how to run and use
the application.

## Design decisions

### One service, two entry points

The web form (Symfony Form) and the REST API (API Platform) both call `ContactService`.
Validation rules live once, as attributes on `ContactInput`, and both entry points run the
same validator. The API cannot accept what the form rejects, or the other way round.

### Mandatory fields

First name and last name are required, and at least one of email and phone. The reason comes
from the output: a contact card without a phone number or an email address cannot be used to
reach anyone. All other fields (birthday, address, organization, job title) are optional.

The "email or phone" rule is enforced twice on purpose: as a validator callback (so the user
gets a message next to the field) and as a database `CHECK` constraint (so no other writer
can store an unreachable contact). A second constraint makes sure no contact is stored
without its QR image. Doctrine does not model `CHECK` constraints, so both are written by hand
in the migrations.

### vCard 3.0

Both vCard and MECARD are recognised by the iOS and Android camera apps. vCard was chosen
because it carries more fields (organization, title, structured address) and is the format
the task names. Version 3.0 has the widest support. The builder follows RFC 2426: CRLF line
endings, escaping of `\ , ;` and line breaks (which also stops "vCard injection" through a
field that contains a line break).

The QR code is generated by endroid/qr-code with error correction level M, as UTF-8.
endroid always adds an ECI header ("these bytes are UTF-8"); there is no option to turn it
off. It is part of the standard. Tests decode the PNG with a PHP port of ZXing;
the served PNG was also decoded with zbar. A test with real iPhone and Android cameras is
still to be done, and it will also show whether the ECI header matters in practice.

### QR images in the database

The PNG is stored in the `contacts` table (`MEDIUMBLOB`), not on the file system. The
database is then the only stateful component: one volume, one backup, and a redeployment
cannot lose the images because the application container holds nothing. The vCard text is
not stored: it is derived from the fields.

### The request log is application data

`request_logs` is an ordinary table with the eight fields the task lists. A `kernel.terminate`
listener writes one row per request (web and API) after the response has been sent, so
clients do not wait for it. It is written with plain SQL (DBAL), not through the ORM: one
INSERT does not need change tracking. The path is stored without the query string. Requests
to `/api` and `/health` count as "API", everything else as "UI". Timestamps have microsecond
precision (`DATETIME(6)`, spelled out because Doctrine's datetime type ignores precision).
Application logs (errors) are separate: Monolog, JSON on stderr in production.

### MariaDB

The job description names MySQL/MariaDB; this application uses MariaDB 11.8 LTS. The
application connects with a user that has rights on its own database only; the root password
is only given to the database container.

One difference to PostgreSQL showed up in testing: MariaDB commits every DDL statement
immediately, so a migration with several `ALTER TABLE` statements that fails halfway leaves
the schema half changed (tested in M2: the columns were added, the constraint failed, the
migration was not recorded, and the next start failed with "Duplicate column"). Migrations
here are written so that each one is safe to apply to the data that exists.

### Migrations at container start

The entrypoint runs `doctrine:migrations:migrate` before FrankenPHP starts. Simple and safe
with one instance; with several instances a separate migration step would be the better choice.

### Caddy terminates TLS, no reverse proxy

FrankenPHP is PHP embedded in the Caddy web server. Caddy gets the certificate from Let's
Encrypt, renews it, redirects HTTP to HTTPS and sets the security headers
(`CADDY_SERVER_EXTRA_DIRECTIVES` in the production compose file). The server runs only this
application, so nothing else needs ports 80 and 443.

The alternative was nginx on the host in front of the container, with certbot. It is the
better choice when several applications share one server (the first deployment of this
project worked that way). Here it would be a second web server, a second configuration and a
certificate renewal to look after, for no gain.

Costs: the app container publishes 80 and 443, and Docker's published ports are not filtered
by `ufw` (here they are meant to be public). The certificate lives in the `caddy-data` volume;
if the volume is lost, Caddy simply gets a new one. The client's IP address reaches the app
directly over IPv4. Over IPv6 Docker would put its own proxy in between and the app would see
Docker's gateway address, so the domain has no AAAA record.

### FrankenPHP classic mode, not worker mode

In worker mode FrankenPHP boots Symfony once and serves many requests from the same process,
which is much faster. It also keeps state between requests: anything static or cached in a
service leaks from one request to the next (for example `Request::setTrustedProxies`). Classic
mode starts every request fresh. For an application of this size the speed is not needed,
and the class of bugs it introduces is not worth it. It can be turned on later with a
`FRANKENPHP_CONFIG` worker line once the services are checked for state.

## Technology choices

| Choice | Why | Alternative |
|---|---|---|
| Symfony 7.4 LTS | long-term support until 2029 | Symfony 8: newer, shorter support |
| API Platform 5 | routes, validation, problem details, OpenAPI 3.2 and Swagger UI from attributes | hand-written controllers plus NelmioApiDocBundle |
| DTO resources, not entities | the API contract stays independent of the database schema; the QR bytes never reach the JSON | `#[ApiResource]` on the Doctrine entity, the common shortcut |
| Plain JSON, not JSON-LD | simple for clients; a list envelope with paging fields | API Platform's default JSON-LD/Hydra |
| FrankenPHP | one binary for web server, TLS and PHP, the official Symfony Docker setup | nginx + PHP-FPM in two processes |
| Stateless CSRF (Symfony 7.2+ default) | no session needed; protection comes from the browser's `Sec-Fetch-Site`/`Origin` headers | session-based tokens |
| Testcontainers | `php bin/phpunit` works the same locally and in CI, against the real database | CI service containers |
| Tests in the production image | no PHP installed on the runner; tests run on the PHP that runs in production | `shivammathur/setup-php`, which downloads and runs installer scripts on the runner |
| Symfony Rate Limiter | built in, one listener in front of both entry points | a reverse proxy limit (nginx `limit_req`) |

## Safe redeployment (task item 8)

Data survives a redeployment because of three things:

1. **One stateful place.** Contacts, QR images and the request log are all in MariaDB. The
   application container holds no data and can be replaced at any time.
2. **A named volume.** The database files are in the Docker volume `qr-php_db-data`. It is
   not deleted by `docker compose up`, `down`, a new image or a server restart; only an
   explicit `docker compose down -v` would delete it.
3. **The deployment never touches the database container.** `qr-deploy` runs
   `docker compose pull app` and `docker compose up -d app`: only the app container is
   recreated. Schema changes arrive as Doctrine migrations, which add to the schema.

On top of that, a deployment whose new version does not become healthy within 60 seconds is
rolled back to the previous image automatically. The script was tested on the first deployment
of this project with an image that never becomes healthy: it rolled back after 78 seconds and the database container
kept running.

## Security considerations

- **No secrets in the repository or the image.** `.env` holds only defaults; passwords come
  from `.env.local` (not committed) or the environment. On the server they were generated
  there and are kept in a `600` file. `.dockerignore` keeps `.env.local` out of the image.
- **Least privilege in the database.** The app's user has rights on its own database only and
  never sees the root password.
- **The request log is password protected** (HTTP Basic, `LOG_VIEWER_PASSWORD`, compared with
  `hash_equals`) because it holds visitors' IP addresses. Without a configured password it is
  closed. The check runs right after routing and looks at the matched route, not the path:
  a path check missed `/%6cogs`, which the router decodes and serves as `/logs` (found by a
  security review after deployment, fixed, and covered by tests).
- **Proxy headers are not trusted.** `TRUSTED_PROXIES` is empty: no proxy sits in front of the
  app, so an `X-Forwarded-For` header from a client is ignored and cannot fake an IP address.
- **Input:** validation, Twig auto-escaping (tested with a `<script>` name), CSRF protection on
  the form (tested with a cross-site request), parameterised SQL everywhere, `LIKE` wildcards
  escaped, length limits on every column.
- **Containers:** the app runs as a non-root user. Only ports 80 and 443 are public; the database
  is reachable only inside the compose network, and the plain HTTP port 8080 is published only
  on the server's loopback for the deploy script's health check. Requests are limited to 1 MB.
- **CI/CD:** the deploy key can only ask the server to deploy one commit of one app (forced
  command, `restrict`). Actions are pinned to commit SHAs, Composer is pinned, dependencies
  are installed without running their plugins or scripts in the test stage, and the pipeline
  only runs for `main`.
- **Public by design:** the contact form, the history and the contact API have no
  authentication, as the task describes them.

## Known limitations

- Contacts and their API are public, and contact ids are sequential.
- The rate limiter's counters are in the container's filesystem cache: they reset when the
  container is recreated, and several instances would count separately.
- The request log is written row by row.
- Migrations run at container start, fine for one instance only.
- A bad value for `birthday` in the API gets the serializer's technical message
  ("This value should be of type string|null.") instead of a friendly one.
- The QR code has not been tested with real phone cameras yet.
- When the database container is down, the app needs about 2 seconds to find out (Docker's
  DNS, shortened from 7.7 seconds with `dns_opt`).

## What I would improve with more time

- Authentication for the contacts (API keys for the API, a login for the UI), and random,
  non-sequential public ids.
- Database backups to storage outside the server, with a tested restore.
- A separate migration step in the pipeline, with each migration checked for being safe on
  MariaDB (one DDL statement per migration, or idempotent statements).
- Worker mode, after checking every service for state kept between requests.
- Metrics (request rate, latency, error rate) and alerting.
- Edit and delete for contacts, with the QR code regenerated on change.
